# Fit Gate design

Date: 2026-07-14
Status: approved, not yet implemented

## Why

job-hound helps the operator pursue jobs. It has no step that tells him not to. Every
artifact it produces (tailored resume, cover letter, prep pack) is generated by
a process that has already assumed the job is a fit and works backward to prove
it. Confirmation bias is baked into the pipeline.

This cost a real interview. The Globex "Senior Staff Operations Engineer, AIOps"
posting listed "data catalog architecture" and "correlation" as areas of deep
expertise, and "Proficient in Python or Go" as a requirement. the operator has neither.
Both were visible in the JD on day one. job-hound generated a full package and a
weekend went into ten stories. In the interview the hiring manager probed exactly
those two things, found nothing, and disengaged. The gap was knowable before he
applied.

Note the failure was not an absence of signal. `fit.py` already scored the role,
and `profile.yaml` already listed `proficient in go` as a coding-bar marker worth
-15 points. The signal existed and was soft, so it lost. **A gate that cannot
block is a report.** This feature is the first component in job-hound empowered
to say "do not apply."

## Scope

In scope: a blocking, per-requirement fit gate; a capabilities and DO-NOT-CLAIM
ledger; a gap tracker; a fit report artifact.

Out of scope (fast-follows once the gate is proven): a lead inbox gaps page,
Discord nagging on open gaps, multi-user gap owners, and any feedback loop that
automatically tunes the prompt from past rulings. Rulings are recorded now, but
nothing consumes them yet.

## Architecture

A new module, `gate.py`. Deliberately not part of `fit.py`: that file is a soft
ranker whose job is to sort leads by attractiveness, and this is a disqualifier
whose job is to say no. Keeping them apart stops the ranker's optimism from
leaking into the gate.

`gate.py` follows the existing convention of `run_scan` and `fit.verdict`: it is
import-safe, side-effect-free, and takes an injectable `call` so it tests offline
with no network.

```
scan -> discovered            (fit.py ranker only; free, no gate)
            |
            |  jh queue <ident>   /   jh fetch <url>
            v
      [ FIT GATE ]  gate.py, one LLM call, reads the full JD
            |
            v
   PROCEED | CONDITIONAL | NEEDS REVIEW | DO NOT APPLY | ERROR
            |
            v
        queued  ->  draft       BLOCKED unless PROCEED or recorded override
```

### The fail-closed spine

The LLM never renders the verdict. It produces evidence; Python renders the
verdict.

```
LLM  ->  extract requirements VERBATIM (quoted, never paraphrased)
     ->  classify each HARD or SOFT, with a confidence
     ->  propose HAVE / PARTIAL / NONE, with cited evidence

CODE ->  HAVE with empty evidence          => demoted to NONE
     ->  PARTIAL with no written bridge    => demoted to NONE
     ->  requirement touches do_not_claim  => FORCED to NONE, LLM overruled
     ->  compute the decision (see arithmetic below)
```

All three demotion rules are one-directional. Code can only make a verdict
harsher, never softer, and no code path upgrades a NONE. This is what makes
"bias toward NONE when evidence is thin" an invariant rather than a request the
model can talk itself out of.

### Decision arithmetic

Computed in Python from the enforced requirement list. Monotone: unresolved items
can only ever make the decision worse, never rescue it.

```
known_hard_none >= 2          -> DO NOT APPLY   (final; adjudication cannot rescue it)
else if unresolved > 0        -> NEEDS REVIEW   (blocks; the operator rules, then recompute)
else if known_hard_none == 1  -> CONDITIONAL    (blocks until every hard gap has a plan)
else                          -> PROCEED
```

Where `known_hard_none` counts requirements that are confidently HARD and, after
enforcement, NONE. `unresolved` counts requirements whose HARD/SOFT classification
came back low-confidence AND whose verdict is NONE or PARTIAL. A low-confidence
classification on a requirement the operator clearly HAS is not unresolved, because the
answer is the same either way. Adjudication therefore only happens when the
ruling could actually change the outcome.

Everything except PROCEED blocks artifact generation. What lifts each block:

- `NEEDS REVIEW`: the operator rules on each unresolved item (`jh gate-rule`). The decision
  is then recomputed from the stored `gate_json` with no API call, and lands on one
  of the other four.
- `CONDITIONAL`: the block lifts once every hard gap has a plan, an hours estimate,
  and a deadline. The decision itself **stays** CONDITIONAL, because it is a record
  of what was true about the role, not a status that gets cleared. Applying is fine;
  applying while unprepared for a known gap is not.
- `DO NOT APPLY` and `ERROR`: only an explicit recorded override (`jh gate-override`,
  mandatory written reason) lifts the block.

### UNSURE: what may and may not be uncertain

Only **classification** (is this bullet hard or soft?) may be UNSURE. That is a
reading-comprehension question and the operator adjudicates it better than the model does.

**Evidence** may never be UNSURE. Whether the operator has data catalog architecture is
not a matter of opinion, and thin evidence always resolves to NONE. This boundary
is what keeps the escape hatch from becoming a loophole. If evidence uncertainty
were allowed to defer to the operator, the confirmation bias would simply relocate.

### Errors fail closed

No API key, malformed JSON, an empty or unfetchable JD, or a network failure all
produce `ERROR`, and `ERROR` blocks drafting exactly as `DO NOT APPLY` does. A
gate that fails open is not a gate.

## The and/or trap

This is the crux of the feature and the exact distinction that was missed. The
Globex JD contains three "or"-ish constructions that are not the same thing:

| JD text | Class | Why |
|---|---|---|
| "15+ years across AIOps, data catalog architecture, product development, and/or Technical Operations infrastructure" | SOFT | Hedged across distinct domains. Any one item satisfies it. |
| "Deep expertise in ... AI/automation, data catalog architecture, workflows, and correlation" | HARD, splits into 4 | Conjunctive list of focus areas, no hedge, under an expertise heading. |
| "Proficient in Python or Go" | HARD | The "or" is between interchangeable instances of one competency, not a hedge across domains. Proficiency in a language is required; which language is the candidate's choice. the operator has neither. |

The third row is what a naive rule gets wrong: it sees "or" and calls it soft.

Two extraction rules follow, and both must be encoded in the prompt and pinned by
the fixture test:

1. A conjunctive list under a hard heading **splits into one requirement per
   item**. This is what turns a single Globex bullet into `data catalog
   architecture` and `correlation` as two separate hard NONEs.
2. "or" between interchangeable instances of one competency stays HARD. "and/or"
   across distinct domains is SOFT.

Net on the fixture: three hard NONEs, so DO NOT APPLY, settled before any UNSURE
item is consulted.

## Data model

### master_resume.yaml

Gains two sections. This file, not a new one, because it is already the accuracy
boundary the generator may not claim outside of. One truth file means no drift,
and `do_not_claim` protects drafting as well as gating.

```yaml
capabilities:
  - claim: multi-account AWS governance
    evidence: Northwind Commerce, 10-account AWS Organization, Dec 2024 to July 2026

do_not_claim:
  - hand-writing production code   # he directs AI tools and judges the output
  - data catalog architecture
  - event correlation
  - high-throughput streaming platforms (Kafka/Kinesis) built from the ground up
```

A claim with no evidence is not a capability and the loader rejects it.

### jobs table

Additive columns, registered in the existing `ADDED_COLUMNS` migration so the
363-row production DB on the tools host migrates in place. Nothing destructive.

- `gate_decision` TEXT
- `gate_json` TEXT (the full structured requirement list, including any rulings)
- `gate_report_path` TEXT
- `gate_at` TEXT
- `gate_override_reason` TEXT
- `gate_overridden_at` TEXT

`gate_json` persists the structured output so that recomputing the decision after
an adjudication costs zero API calls, and so rulings accumulate as a corpus for
later prompt tuning.

### gaps table (new)

```
id, job_uid, requirement, plan, hours_estimate, deadline,
status (open|closed), created_at, closed_at
```

Owner is implicit: it is always the operator. A CONDITIONAL job cannot draft until every
hard gap has a plan, an hours estimate, and a deadline. That is the mechanism that
stops a gap from being logged and admired.

## Where the block bites

**In `job_generate.generate()`, not in the CLI.** Every artifact goes through that
one function, and so does the MCP `job_draft` tool that the chat agent calls from Discord.
Guarding the CLI alone would leave the Discord path open. One guard at the choke
point, and the CLI, MCP, and any future GUI all inherit it.

The CLI additionally prints a friendly, actionable message rather than a raw
exception.

## CLI surface

```
jh gate <ident>                     run or re-run the gate; print and store the report
jh gate-rule <ident> <n> --hard|--soft [--note "..."]
                                    adjudicate an UNSURE item; recomputes, no API call
jh gate-override <ident> --reason "..."
                                    explicit recorded override; reason is mandatory
jh gaps [<ident>]                   open gaps, all or per job
jh gap-close <id>
```

`queue` and `fetch` run the gate automatically, since both are the moment intent
is expressed.

## The fit report artifact

`fit-report.md`, written into the application package folder (reusing
`job_generate`'s existing folder helper, created at gate time rather than draft
time so the report exists when the decision is made). Contains every requirement
with its verbatim quote, its classification, its verdict, the cited evidence or
the explicit absence of it, any UNSURE items, the title check, the gap list, and
the decision.

Voice: no em dashes, per the project's hard rule. Reuse the existing `_no_dash`
safety net.

## Title check

Compares the title's role-noun (Engineer / Manager / Architect / Lead / Staff)
against how the operator actually works, and flags a mismatch. "Senior Staff Engineer"
predicts live coding and code review whatever the JD emphasizes.

Per the operator's decision on 2026-07-14, this is a **flag, not a blocker**: it appears
prominently in the report but does not itself change the decision arithmetic.

## Testing

Two layers, because a test with a canned LLM response only tests the fixture, not
the prompt.

**Offline unit tests** (run in CI, free, no network, injected `call`):
- each demotion rule, individually
- `do_not_claim` forces NONE even when the LLM returns HAVE with confident evidence
- the decision arithmetic at each boundary (0, 1, 2 hard NONE; unresolved present)
- monotonicity: no input produces a decision softer than its known_hard_none allows
- fail-closed on malformed JSON, missing key, empty JD
- the title check
- CONDITIONAL blocks draft until gaps have plan, hours, and deadline
- the block bites in `generate()`, so the MCP path is covered too

**Live fixture test** against the real Globex JD (`tests/fixtures/aiops-platform-jd.md`),
skipped when `ANTHROPIC_API_KEY` is absent so CI stays green and free. Asserts:

- decision is `DO NOT APPLY`
- hard NONE: data catalog architecture
- hard NONE: correlation
- hard NONE: Proficient in Python or Go
- the "15+ years across ... and/or ..." bullet is classified SOFT
- title mismatch is flagged

This is the tuning loop. Per the acceptance criteria: if the gate does not fail
this posting, it is too soft and is not doing its job. Iterate the prompt against
this fixture until it fails.

## Risks

- **The gate drifts soft over time as the prompt is edited.** Mitigated by the
  live fixture test, which is the regression barrier. It must stay in the repo and
  be run before any prompt change is merged.
- **the operator overrides habitually and the gate becomes theater.** Mitigated only by
  the mandatory written reason and the audit trail in `state_log`. Worth reviewing
  the override log after a few months; a high override rate means the gate is
  miscalibrated, not that the overrides were wrong.
- **An LLM call is now on the `queue` path**, so queueing costs money and can fail.
  Acceptable: queueing is a handful of jobs a week, and failure fails closed.
